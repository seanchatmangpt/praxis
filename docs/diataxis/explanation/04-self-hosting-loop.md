# The Self-Hosting Loop, Explained

`crates/ggen` is a Rust crate with a CLI. Its own CLI routes — the noun-verb
functions that `clap_noun_verb` dispatches into, for `sync`, `graph`,
`receipt`, `doctor` — are not written by a person. They are rendered by
`ggen sync`, the same tool the crate implements, reading the same
`schema/praxis.ttl` the crate reads for everything else
(`crates/ggen/src/verbs/mod.rs:1-8`, `crates/ggen/src/verbs/sync.rs:1-4`).
The generator generates its own front door. That loop, and what it costs and
buys, is the subject of this note.

## Two tools, one name, easy to conflate

It is worth being precise about which binary does what, because the two are
easy to confuse and the confusion matters for what follows.

The globally installed `ggen` (`/Users/sac/.cargo/bin/ggen`, reporting
`ggen 26.7.2` when invoked) is built from the separate `/Users/sac/ggen`
workspace — the mature, ten-crate μ₁–μ₅ pipeline described in that project's
own `CLAUDE.md`: *"Formula: A = μ(O) — Code precipitates from RDF via
five-stage pipeline (μ₁-μ₅)"* (`/Users/sac/ggen/CLAUDE.md:3`). It is this
binary that reads root `/Users/sac/praxis/ggen.toml` and executes
`[[generation.rules]]` entries — SPARQL query, Tera template, output path,
write mode. Running it confirms this directly:

```
$ /Users/sac/.cargo/bin/ggen --version
ggen 26.7.2
```

`crates/ggen` inside praxis is a *different*, smaller, self-hosted
reimplementation of the same idea — its own `GgenConfig` loader
(`crates/ggen/src/config.rs:19-27`) only recognizes `[project]`,
`[ontology]`, `[packs]`, `[templates]` (with `#[serde(deny_unknown_fields)]`
on every table), and has no `generation.rules` field at all. Feeding it the
real root `ggen.toml` verbatim fails closed with exactly the error you would
expect from an unknown-key rejection:

```
Error: Command execution failed: config error: [FM-CONFIG-002] invalid ggen.toml at
`.../ggen.toml`: TOML parse error ... unknown field `generation`, expected one of
`project`, `ontology`, `packs`, `templates`. Remediation: fix the TOML syntax or
remove unknown keys.
```

So the self-hosting loop is not "the crate generates itself in isolation." It
is: the mature external `ggen` (root ontology, root `ggen.toml`, the
`crate-ggen-verbs-*` rules at `ggen.toml:179-315`) generates the *routes* of
the newer, smaller crate that is bootstrapping toward eventually replacing
it. One generator's output is another generator's front door. That nesting
is deliberate — it is how a codebase migrates onto its own paradigm without
a flag day: the new crate proves out the ontology-driven CLI shape while the
old, load-bearing pipeline still does the actual rendering.

## Why generate the routes instead of hand-writing them

The comment at the top of every generated route file says the same thing
three times over: "GENERATED by `ggen sync` from `schema/praxis.ttl`
(`praxis:CliCommand` instances). Do not edit by hand: routes are a pure
projection of the ontology" (`crates/ggen/src/verbs/sync.rs:1-4`,
`crates/ggen/src/verbs/mod.rs:1-8`). The instinct to ask "why not just write
`fn sync_run(dry_run: bool, watch: bool) { ... }` by hand, it's four lines"
is reasonable on its face — and it is exactly the instinct the whole
architecture is built to resist, because the four-line function is never
really four lines. It's four lines *plus* the obligation to keep them in
sync, by discipline, with every other place the same fact is asserted:
the flag's existence, its name, which noun/verb it belongs to, what it does,
and what handler receives it.

The ontology is where those facts live exactly once. `schema/praxis.ttl`
defines `praxis:CliCommand` as a class (`schema/praxis.ttl:43-45`) and gives
each command its `noun`, `verb`, `handler`, `inCrate`, and zero or more
`flag` triples (`schema/praxis.ttl:134-159`). The `sync run` command itself
is one instance:

```turtle
praxis:CmdGgenSyncRun a praxis:CliCommand ;
    praxis:inCrate praxis:CrateGgen ;
    praxis:noun "sync" ;
    praxis:verb "run" ;
    praxis:handler "handle_sync_run" ;
    praxis:flag "dry_run" ;
    praxis:flag "watch" ;
    rdfs:comment "Run the five-stage generation pipeline: resolve, enrich, extract, render, write. --watch re-runs the pipeline on filesystem changes." .
```
(`schema/praxis.ttl:259-266`)

`ggen.toml`'s `crate-ggen-verbs-sync` rule (`ggen.toml:196-224`) is a SPARQL
projection of that instance data, and `templates/crates/ggen/verbs_noun.rs.tera`
(the whole file, 16 lines) turns each result row into a `#[verb(...)]`
function whose parameters are exactly the `flag` values, passed positionally
into `crate::verbs::handlers::{{ row.handler }}(...)`
(`templates/crates/ggen/verbs_noun.rs.tera:8-14`). Add a flag to the
ontology and every one of those places — the CLI usage string, the function
signature, the call into the handler — updates from one edit, because they
were never independently-typed facts to begin with; they were one fact,
projected five ways.

This is the same commitment that shows up in the project's own iron
invariants, restated for a different surface. Invariant 2 says receipts "are
computed, never asserted" — the pattern of writing down a value by hand that
the system should instead be deriving is named and refused
(`CLAUDE.md:25-28`, praxis root). A hand-written route is the CLI-surface
version of an asserted value: a human declares "the `sync run` command takes
`dry_run` and `watch`," and nothing checks that declaration against the
ontology that is supposed to be the one source of that fact. Generating the
route instead makes the ontology the only place that assertion can be made,
and everything downstream a computation over it — which is the same move
`A = μ(O)` makes at the level of a whole codebase (`/Users/sac/ggen/CLAUDE.md:3`):
code is not written, it precipitates from `O`. Praxis's own framing of the
same idea, one level more abstract, is the Post-Chatman equation
`A ≅ O ≅ L` — application, ontology, and logic held isomorphic, with the
ontology as declarative ground truth (`docs/ontology.md:5`). A generated CLI
route is a small, concrete instance of that isomorphism: the shape of the
function is not a decision anyone made about the function; it is a
projection of a decision made about the domain, `O`.

## What this buys, concretely

The obvious win is that `ggen graph validate`'s route, `ggen receipt
verify`'s route, and `ggen doctor run`'s route are all one Tera template
(`templates/crates/ggen/verbs_noun.rs.tera`) applied four times
(`ggen.toml:196-314`), rather than four hand-maintained files that happen to
look similar today and drift independently tomorrow. Add a fifth noun to
`schema/praxis.ttl` and a fifth `[[generation.rules]]` block, and the CLI
surface grows without anyone touching Rust syntax for the routing layer
itself — only `crates/ggen/src/verbs/handlers.rs` needs a matching function,
and that file's own module doc says as much: "The route files ... are pure
projections of `schema/praxis.ttl` ... only this module carries logic"
(`crates/ggen/src/verbs/handlers.rs:1-5`).

The less obvious win, and the reason this is worth an explanation document
rather than a one-line comment, is that the generated file becomes evidence
of what the ontology says, checkable by diff. Run the (external) `ggen sync`
against a scratch copy of the real project and the receipt records exactly
what changed:

```
$ ggen sync --dry_run false   # run inside a disposable scratch copy, not the real repo
...
{
  "action": "created",
  "path": "./crates/ggen/src/verbs/sync.rs",
  "rule": "crate-ggen-verbs-sync",
  "size_bytes": 597
},
...
"files_synced": 11,
"generation_rules_executed": 11,
"receipt_path": ".ggen/receipts/latest.json",
"status": "success"
```

That receipt is a claim about the whole sync, hash-addressed
(`.ggen/receipts/latest.json`, per the rule's own `output_file` bookkeeping)
— not a human's say-so that "the routes are up to date."

## What can still go wrong: the GROUP_CONCAT flag-swap

Generation does not eliminate risk; it relocates it, from "did the human
forget to update this file" to "did the projection preserve the fact it was
supposed to preserve." The `crate-ggen-verbs-sync` rule is a good worked
example of the relocated risk because it is subtle enough to survive
`cargo build` clean.

The rule's SPARQL aggregates each command's flags with `GROUP_CONCAT`, and
the *order* of that concatenation is controlled entirely by the inner
subquery's `ORDER BY ?flag`:

```sparql
SELECT ?noun ?verb ?handler ?comment (GROUP_CONCAT(?flag; separator=",") AS ?flags)
WHERE {
  {
    SELECT ?cmd ?noun ?verb ?handler ?comment ?flag
    WHERE { ... FILTER(?noun = "sync") }
    ORDER BY ?flag
  }
}
GROUP BY ?noun ?verb ?handler ?comment
ORDER BY ?verb
```
(`ggen.toml:201-220`)

The template then splits `?flags` on commas and emits each one, in that
order, both as a function parameter and as a positional argument to the
handler (`templates/crates/ggen/verbs_noun.rs.tera:9-13`). Nothing in that
chain is keyed by name once it reaches Rust — it is purely positional. The
hand-written handler it calls into is, and has to remain, in the matching
order:

```rust
pub fn handle_sync_run(dry_run: bool, watch: bool) -> Result<serde_json::Value> {
```
(`crates/ggen/src/verbs/handlers.rs:36`)

Both parameters are `bool`. That is the whole hazard: Rust's type checker
enforces arity and type, not which `bool` is which. If the inner `ORDER BY
?flag` in `ggen.toml:216` were reversed — `ORDER BY DESC(?flag)` instead of
`ORDER BY ?flag` — the projection still produces two well-typed booleans, in
the other order. Reproducing this against a scratch copy of the project
(never the real repo) makes the failure concrete rather than hypothetical:
with `ORDER BY ?flag` unchanged, `ggen sync` regenerates exactly the
baseline route,

```rust
fn sync_run(dry_run: bool, watch: bool) -> Result<serde_json::Value> {
    crate::verbs::handlers::handle_sync_run(dry_run, watch)
}
```

and with only that one `ORDER BY ?flag` flipped to `ORDER BY DESC(?flag)` in
the scratch copy's `ggen.toml`, re-running `ggen sync` regenerates

```rust
fn sync_run(watch: bool, dry_run: bool) -> Result<serde_json::Value> {
    crate::verbs::handlers::handle_sync_run(watch, dry_run)
}
```

That compiles. `handle_sync_run`'s signature is `(dry_run: bool, watch:
bool)` (`crates/ggen/src/verbs/handlers.rs:36`); the flipped call site
passes the CLI's `--watch` value into the `dry_run` slot and the CLI's
`--dry-run` value into the `watch` slot, entirely by position. The doc
comment on the handler spells out what each argument is supposed to mean —
"`dry_run` computes every write decision without touching the filesystem or
emitting a receipt. `watch` runs one sync then blocks ... in practice it
never returns" (`crates/ggen/src/verbs/handlers.rs:27-30`) — and the
implementation branches on `watch` first, calling `crate::watch::watch(&root,
dry_run)` which blocks (`crates/ggen/src/verbs/handlers.rs:38-39`). With the
arguments swapped, passing `--dry-run` would land in the `watch` parameter
and enter the blocking branch instead of the intended no-op preview; passing
`--watch` would land in the `dry_run` parameter and run once without ever
watching. Every unit test that calls `handle_sync_run` with named
constants would still pass, because the function itself is unchanged — only
the generated caller's argument order moved. No compiler error, no clippy
lint, no type mismatch: two `bool`s swapped is invisible at every layer
that only checks types.

This is exactly the failure mode the ordering matters for, and it is why
the `ORDER BY ?flag` in the inner subquery is load-bearing rather than
cosmetic: it is the only thing pinning the projection's parameter order to
a stable, name-derived sequence (lexicographic on the flag string) rather
than to whatever order the triple store happens to enumerate matches in.
Removing that `ORDER BY` — not just reversing it — would make the bug
nondeterministic: correct on one run, silently swapped on the next,
depending on internal iteration order the ontology says nothing about. The
fix for this class of bug, in general, is not "add a code comment warning
future editors" — comments do not participate in the projection and are the
first thing a subsequent regeneration will not touch, but also cannot make
safe. The fix is to make the positional coupling either impossible (name the
parameters, not just order them — e.g. project a struct field per flag
rather than a comma-joined ordinal list) or checked (a test that regenerates
the route from the ontology and asserts the generated source text, so a flag
reordering shows up as a diff a reviewer has to look at, not a change that
type-checks and vanishes). Either repair deepens authority in the same
direction the rest of this architecture already points: the ontology should
be *harder to misproject*, not merely *easy to regenerate from*. A generator
that reliably reproduces last week's bug is not self-hosting; it is
self-perpetuating.
