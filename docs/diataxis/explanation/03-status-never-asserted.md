# Why Status Is Never Asserted

Open either of this session's two packs and search for the properties you'd expect a "breed catalog" or "algorithm catalog" to carry: `breedStatus`, `algorithmStatus`, `standing`. You won't find them asserted anywhere. `packs/wasm4pm-cognition-pack/ontology.ttl` defines exactly five properties on `compat:CognitionBreed` — `breedId`, `breedLabel`, `breedDoc`, `citation`, `modulePath` (`packs/wasm4pm-cognition-pack/ontology.ttl:21-25`) — and none of the 32 breed instances that follow (`compat:Breed_strips` through `compat:Breed_ocpm_route_discoverer`, `packs/wasm4pm-cognition-pack/ontology.ttl:29-383`) carries a status triple. The algorithms pack is the same shape at ten times the property surface: `packs/wasm4pm-algorithms-pack/ontology.ttl:29-70` defines `algorithmId`, `algorithmLabel`, `algorithmDoc`, `citation`, `outputType`, `category`, `speedTier`, `qualityTier`, `wasmExport` — a whole taxonomy of *what an algorithm is and does* — and still no `algorithmStatus`. A `grep -n -i "algorithmStatus\|standing" packs/wasm4pm-algorithms-pack/ontology.ttl` run against the file returns exactly one hit, at line 18, and it's a comment, not a triple:

```
18:#   pi:algorithmStatus / pi:standing / pi:measuredFitness / pi:piAdmitted /
19:#   pi:fitnessProvenance — CONSTRUCT-derived from evidence in wasm4pm.
```

That absence is not an oversight waiting to be filled in on the next pass. It's the point.

## The two ways to put a triple in a graph

A knowledge graph gets its facts from exactly two sources, and the difference between them is the whole story here. You can hand-assert a triple — write `compat:Breed_strips compat:breedStatus "alive"` directly into a `.ttl` file, the same way you'd write `compat:breedId "strips"`. Or you can derive it: run a `CONSTRUCT` query over some other set of triples — evidence, witnesses, receipts — and let the query produce the status triple as output, never as input.

Both produce identical-looking RDF. `?s pi:algorithmStatus "verified"` reads the same whether a human typed it or a query computed it. That's exactly the danger. Once the triple is in the graph, nothing about its syntax tells you which path it came from. The provenance has to be enforced structurally — by what's allowed to appear in a hand-authored ontology file at all — because it can't be recovered from the triple itself after the fact.

The comment block at the top of each pack (`packs/wasm4pm-cognition-pack/ontology.ttl:14-16`, `packs/wasm4pm-algorithms-pack/ontology.ttl:17-21`) is doing exactly this enforcement, in the only place a `.ttl` file can enforce anything: by omission. `breedStatus` doesn't have a domain/range declaration next to `breedDoc` and `citation` because there is no code path in this pack that is allowed to write one. The property isn't banned by a validator here — these packs simply never give it a slot to be asserted into. If a future edit added `compat:Breed_strips compat:breedStatus "alive" .` by hand, it would parse as valid Turtle and merge into the graph without complaint. The only thing standing between "valid Turtle" and "trustworthy claim" is the discipline of never writing that line — a discipline documented in the file's own preamble rather than mechanically forced by this pack's contents.

## Why this discipline, specifically, is worth a whole doc

Status and fitness properties are exactly the properties a consumer of the graph is going to *act on*. A pipeline stage that reads `pi:qualityTier` to sort algorithms by faithfulness is reading descriptive metadata — wrong metadata is an inconvenience. A pipeline stage that reads `pi:algorithmStatus = "admitted"` to decide whether to *route traffic to that algorithm* is reading a trust claim. If that claim can be hand-typed by whoever last edited the ontology file, the graph stops being evidence and becomes opinion with RDF syntax. The whole appeal of "software as admitted projection" — the framing this repo's vision document opens with — evaporates the moment the admission decision can be forged by editing a text file instead of earned by evidence passing through a query.

This is precisely the split the project's own governance pillar names. `/Users/sac/praxis/docs/vision-2030-prd-adr.md` lists, under **P3 — Ontology governance**, requirement **R3.2**: "Asserted-vs-derived split enforced (status/fitness properties only via CONSTRUCT from evidence — never hand-asserted)" (`docs/vision-2030-prd-adr.md:34`). The two packs audited here are a small, concrete instance of that requirement holding: they're catalog/caller surfaces, deliberately scoped to *what an algorithm or breed is* (id, label, doc, citation, category, tiers, module path, wasm export name), and deliberately silent on *whether it's earned trust*. The comment in each file — "breedStatus is NEVER asserted here — it is CONSTRUCT-derived from evidence via the alive-gate in wasm4pm" (`packs/wasm4pm-cognition-pack/ontology.ttl:14-16`); "DERIVED PROPERTIES (never asserted here, by design): pi:algorithmStatus / pi:standing / pi:measuredFitness / pi:piAdmitted / pi:fitnessProvenance — CONSTRUCT-derived from evidence in wasm4pm" (`packs/wasm4pm-algorithms-pack/ontology.ttl:17-19`) — is doing the same job R3.2 does at the requirement level, just localized to two files instead of stated once for the whole ecosystem.

It's also worth noticing what this split does *not* claim. Neither pack asserts that the CONSTRUCT-derived status pipeline in `wasm4pm` is itself bulletproof, correctly wired, or free of its own bugs — that's outside what a `.ttl` catalog file can prove, and outside the scope of what was read for this document. What the split *does* buy is narrower and more defensible: it guarantees that if status is wrong, the bug lives in one auditable place — the evidence-to-CONSTRUCT pipeline — rather than being smearable across every hand-edited ontology file in every pack that happens to reference these breeds and algorithms. A wrong `qualityTier` is a typo. A wrong `algorithmStatus` that got there by typo, in a graph whose entire value proposition is "receipts, not review" (P2 in the same vision document), is a trust failure with no fingerprint. Keeping the derived properties out of every file that *isn't* the CONSTRUCT pipeline is what makes "search one place for the bug" a true statement instead of an aspiration.

## Why this connects to more than two ontology files

The vision document frames this as one of three convergent laws — closed vocabulary, status earned by evidence, chained tamper-evident history — that "all five ecosystem projects independently converged on" (`docs/vision-2030-prd-adr.md:59`, AD-4). Read that way, the empty grep result in these two packs isn't a peculiarity of the wasm4pm domain; it's what R3.2 looks like when you go check a specific file instead of trusting the requirement's prose. The Chatman-Equation framing that ggen itself uses — code as `A = μ(O)`, a deterministic projection of an ontology (see `ggen`'s own workspace description, and R1.1 in the same vision doc: "generated surfaces are projections of an admitted graph via `A = μ(O)`") — depends on the same discipline one level up: if `O` can contain hand-asserted claims dressed up as derived facts, the projection `μ(O)` inherits a forgeable input, and the whole determinism argument for trusting generated code quietly stops applying to the parts of `O` that were never actually earned. Keeping `breedStatus` and `algorithmStatus` out of the hand-authored packs is a small, checkable instance of keeping the ontology itself honest — which is the precondition for everything downstream that claims to be *derived* from it.
