Observed behavior: unlike `sync`, `graph`, and `doctor`, `ggen receipt --help` prints the help of the `verify` verb directly rather than listing `receipt`'s subcommands (`history`, `verify`). Running `ggen receipt` with no verb and no `--help` in a directory with no `.ggen-v2/receipt.json` produced:

```
$ ./target/debug/ggen receipt
Error: Command execution failed: receipt `/Users/sac/praxis/.ggen-v2/receipt.json` unreadable: No such file or directory (os error 2)
```

This confirms the bare noun `receipt` defaults to the `verify` verb at runtime, consistent with `RECEIPT_REL_PATH` being read by `handle_receipt_verify` (`crates/ggen/src/verbs/handlers.rs:100`). The default-verb mapping is applied by `inject_default_verbs` before dispatch (`crates/ggen/src/main.rs:21`).

`receipt` registers two verbs in source order: `history` (`crates/ggen/src/verbs/receipt.rs:11-14`) and `verify` (`crates/ggen/src/verbs/receipt.rs:18-21`).

## Verified exit-code behavior

Running a verb against a project whose `ggen.toml` fails to parse:

```
$ ./target/debug/ggen doctor run
Error: Command execution failed: config error: [FM-CONFIG-002] invalid ggen.toml at `/Users/sac/praxis/ggen.toml`: TOML parse error in /Users/sac/praxis/ggen.toml: TOML parse error at line 3, column 1
  |
3 | version = "26.6.0"
  | ^^^^^^^
unknown field `version`, expected `name`
$ echo $?
1
```

This was run from `/Users/sac/praxis` in this session; `$?` reported `1`, confirming that a handler-level error (here, `GgenConfig::load` failing inside `handle_doctor`, `crates/ggen/src/verbs/handlers.rs:355`) propagates to a non-zero process exit through `exec_err` (`crates/ggen/src/verbs/handlers.rs:23-25`) and `main`'s `registry.run(args).map_err(...)` (`crates/ggen/src/main.rs:34`).
