# How to Reference a Git Pack (and Why You Cannot Yet)

You want to declare a pack in `[packs]` that points at a Git URL (`{ git =
"...", version = "..." }`) instead of a local `path =`, so a team can share a
pack from a repository without vendoring a copy per project. Today this
fails closed — this guide shows the real error and the workaround.

This assumes you already have a working `ggen.toml` + ontology + template
project; if you don't, do [Your First Pack](../tutorials/02-your-first-pack.md)
first.

## The problem in one sentence

`PackRef::Git` is a real, parseable variant of the `[packs]` schema, but
`resolve()` refuses every git pack unconditionally with `FM-PACK-007` —
there is no cloning, fetching, or version-resolution implementation behind
it yet.

## What happens today if you try it

`[packs]` accepts two shapes, both defined on `PackRef`
(`crates/ggen/src/config.rs:53-66`):

```rust
pub enum PackRef {
    /// Local pack: `{ path = "…" }`.
    Path {
        /// Filesystem path to the pack directory.
        path: PathBuf,
    },
    /// Remote pack: `{ git = "…", version = "…" }`.
    Git {
        /// Git repository URL.
        git: String,
        /// Version requirement (tag or semver).
        version: String,
    },
}
```

The manifest parses fine with a `git = ...` entry — it's `resolve()` that
refuses it. The match arm, verbatim (`crates/ggen/src/pack.rs:68-77`):

```rust
PackRef::Git { git, version } => {
    return Err(AppError::fm_pack(
        7,
        format!(
            "pack `{name}`: git packs are not implemented \
             (git = `{git}`, version = `{version}`). \
             Remediation: vendor the pack locally and use {{ path = \"…\" }}."
        ),
    ));
}
```

The docstring on `resolve()` lists this as a known, documented error code,
not an oversight (`crates/ggen/src/pack.rs:63`):

```
/// - `[FM-PACK-007]` `PackRef::Git` (git packs are not implemented)
```

### Reproducing it

In a scratch project (`/tmp/ggen-git-pack-demo`):

```toml
# ggen.toml
[project]
name = "git-pack-demo"

[ontology]
source = "ontology.ttl"

[packs]
widget = { git = "https://github.com/example/widget-pack.git", version = "1.0.0" }

[templates]
dir = "templates"
```

```
$ ggen sync run
```

Real output (binary built via `cargo build -p ggen` from the workspace root,
run from `/tmp/ggen-git-pack-demo`):

```
Error: Command execution failed: validation error: [FM-PACK-007] pack `widget`: git packs are not implemented (git = `https://github.com/example/widget-pack.git`, version = `1.0.0`). Remediation: vendor the pack locally and use { path = "…" }.
```

(Followed by a Rust backtrace from `ggen::main`, `crates/ggen/src/main.rs:35`
— the process exits non-zero either way.)

## The workaround: vendor the pack locally

The error message tells you the remediation directly: clone the pack's
repository yourself, then reference the clone with `{ path = "…" }`
(`PackRef::Path`, resolved by `resolve_path_pack` at
`crates/ggen/src/pack.rs:87`, which only ever checks `root.is_dir()` — it
never talks to a VCS).

### 1. Clone the pack's source into your project (or next to it)

```bash
$ git clone https://github.com/example/widget-pack.git vendor/widget-pack
```

(This guide's demo used a local stand-in repo instead of a real GitHub URL,
to run inside a scratch dir with no network access; the command shape is
identical to cloning a real remote.)

### 2. Point `path =` at the clone

```toml
[packs]
widget = { path = "vendor/widget-pack" }
```

### 3. Sync — real output, `FM-PACK-007` is gone

```
$ ggen sync run
{
  "decisions": {
    "src/widget.rs": "written"
  },
  "graph_hash_hex": "1e885fdf13f2d4d1404905bb7bfa80b6e5768de41672de5bc832f979de8eb0d4",
  "packs": {
    "widget": "88e48953d26ef8c46676aeb6df3e6e88967294133b821c25d2ccfda57040e6ed"
  },
  "skipped": [],
  "written": [
    "src/widget.rs"
  ]
}
```

`src/widget.rs` on disk, read back for real:

```rust
//! Generated by the demo-pack widget template. Do not edit.

/// Widget precipitated from the pack ontology.
pub struct Widget {
    pub count: String,
    pub name: String,
}
```

### 4. Pin the version yourself

Since `resolve()` never reads `version` for a `Git` ref (it can't — that arm
always errors before touching the field) and `Path` packs carry no version
field at all, pinning is on you: `git checkout <tag>` inside `vendor/widget-pack`
before committing it, or vendor a fresh clone per release and update `path =`
to point at the new directory. `content_hash` (used for the `packs` entry in
the receipt above) hashes the pack's ontology + templates
(`crates/ggen/src/pack.rs:9-10`), so a changed vendor tree changes the
receipt's pack hash even if you forget to bump anything by hand — that's
your only automatic drift signal today.

## Gotchas

- **The error is unconditional, not feature-gated.** There is no flag, env
  var, or nightly build that makes `{ git = ... }` resolve — every
  `PackRef::Git` hits the same `return Err(...)` at
  `crates/ggen/src/pack.rs:69`, regardless of whether the URL is reachable.
  Don't waste time debugging network/auth — the request never leaves the
  process.
- **`vendor/` is a convention, not a requirement.** `resolve_path_pack`
  joins `path` onto `config_root` (`crates/ggen/src/pack.rs:88`) — any
  relative path works, including a clone that lives outside your project
  tree (`path = "../widget-pack"`), as the existing
  `crates/ggen/examples/demo-project/ggen.toml:8` does.
- **Don't hand-edit inside the vendored clone.** Nothing stops you from
  editing files under `vendor/widget-pack` directly, but doing so silently
  diverges from upstream with no record of what changed — treat the clone
  as read-only and re-clone (or re-checkout) to update.
- **`source_string()` still reports what you declared**, not what's on
  disk: for a resolved `Path` pack it's `path:<dir>`, and for the
  (unreachable) `Git` shape it would be `git:<url>@<version>`
  (`crates/ggen/src/pack.rs:239-243`) — useful if you're grepping logs for
  which packs are still git-shaped and need vendoring.
