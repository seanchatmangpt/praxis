# Composing Two Packs

In this tutorial you build two tiny, independent ggen packs from scratch, wire
both into one project's `[packs]` table, and run a single sync that produces
both packs' outputs at once. You'll finish with a `ggen.lock` that lists both
packs, sorted alphabetically, each pinned to a content hash.

You need a working `ggen` binary. If you haven't built one yet, from the
repository root run:

```bash
cargo build -p ggen
```

This produces `target/debug/ggen`. Everything below runs that binary
directly, so substitute the full path to it if it isn't on your `PATH`.

## 1. Make a scratch workspace

Do this work outside the repository, in a throwaway directory, so nothing you
create here touches the real project.

```bash
mkdir -p /tmp/ggen-tutorial-05
cd /tmp/ggen-tutorial-05
```

You'll end up with three sibling directories here: two packs and one
consumer project.

## 2. Build the first pack: `greeter-pack`

A pack is a directory holding `pack.toml`, `ontology.ttl`, and a
`templates/` directory of `*.tmpl` files
(`crates/ggen/src/pack.rs:1-9`). Create it:

```bash
mkdir -p greeter-pack/templates
```

Create `greeter-pack/pack.toml`:

```toml
[pack]
name = "greeter-pack"
version = "0.1.0"
description = "Generates a hello-world greeting module."
```

The `[pack]` table only accepts exactly these three keys — `name`,
`version`, `description` — nothing else
(`crates/ggen/src/pack.rs:38-47`).

Create `greeter-pack/ontology.ttl`:

```turtle
@prefix gp:   <http://example.org/packs/greeter#> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

gp:Greeting
    a          rdfs:Class ;
    rdfs:label "Greeting" .

gp:HelloGreeting
    a          gp:Greeting ;
    rdfs:label "Hello" .
```

Create `greeter-pack/templates/greeter.rs.tmpl`:

```
---
to: src/greeter.rs
sparql:
  greetings: >
    PREFIX gp: <http://example.org/packs/greeter#>
    PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
    SELECT ?label WHERE {
      ?g a gp:Greeting ; rdfs:label ?label .
    } ORDER BY ?label
---
//! Generated by greeter-pack.
{% for g in greetings %}pub fn say_{{ g.label | lower }}() -> String {
    "{{ g.label }}, world!".to_string()
}

{% endfor %}
```

The frontmatter's `to:` key sets the output path (relative to the consuming
project), and each entry under `sparql:` binds a query result to a variable
name usable in the template body — this is the same shape used by the
shipped `star-toml-pack` template
(`packs/star-toml-pack/templates/star_toml_config.rs.tmpl:1-15`).

## 3. Build the second pack: `farewell-pack`

Its output path (`src/farewell.rs`) is deliberately disjoint from
`greeter-pack`'s (`src/greeter.rs`), so both packs can write into the same
project without colliding.

```bash
mkdir -p farewell-pack/templates
```

Create `farewell-pack/pack.toml`:

```toml
[pack]
name = "farewell-pack"
version = "0.1.0"
description = "Generates a farewell module."
```

Create `farewell-pack/ontology.ttl`:

```turtle
@prefix fp:   <http://example.org/packs/farewell#> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

fp:Farewell
    a          rdfs:Class ;
    rdfs:label "Farewell" .

fp:ByeFarewell
    a          fp:Farewell ;
    rdfs:label "Goodbye" .
```

Create `farewell-pack/templates/farewell.rs.tmpl`:

```
---
to: src/farewell.rs
sparql:
  farewells: >
    PREFIX fp: <http://example.org/packs/farewell#>
    PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
    SELECT ?label WHERE {
      ?f a fp:Farewell ; rdfs:label ?label .
    } ORDER BY ?label
---
//! Generated by farewell-pack.
{% for f in farewells %}pub fn say_{{ f.label | lower }}() -> String {
    "{{ f.label }}, world!".to_string()
}

{% endfor %}
```

## 4. Create the consuming project

```bash
mkdir -p myproj/templates
echo "" > myproj/ontology.ttl
```

Create `myproj/ggen.toml`, referencing both packs by relative path:

```toml
[project]
name = "myproj"

[ontology]
source = "ontology.ttl"

[packs.greeter-pack]
path = "../greeter-pack"

[packs.farewell-pack]
path = "../farewell-pack"

[templates]
dir = "templates"
```

Every top-level table here — `[project]`, `[ontology]`, `[packs.<name>]`,
`[templates]` — is exactly what `GgenConfig` parses; each pack entry is a
`PackRef::Path { path }` (`crates/ggen/src/config.rs:16-66`). Note that
`[packs]` is a `BTreeMap`, so the order you write the two `[packs.*]` tables
in has no effect on the result — only the pack *names* matter, and those get
sorted for you.

## 5. Run sync

```bash
cd myproj
/path/to/target/debug/ggen sync run
```

You should see JSON output naming both packs and both files as written, for
example:

```json
{
  "decisions": {
    "src/farewell.rs": "written",
    "src/greeter.rs": "written"
  },
  "graph_hash_hex": "f8d1c10fb6281905c580179bd8475c06973dc244ff4cf371e6770a2a7483ce85",
  "packs": {
    "farewell-pack": "3a5273f8d7ad156c24d3113174eb979cf485587439d34e7c9d7d035c5e071aac",
    "greeter-pack": "be1d7ac715f5c839483cdf4318891234164e6054e8ebad69cdfa6ca8fb1ca81a"
  },
  "skipped": [],
  "written": [
    "src/farewell.rs",
    "src/greeter.rs"
  ]
}
```

## 6. Check both outputs

```bash
cat src/greeter.rs
cat src/farewell.rs
```

`src/greeter.rs` contains:

```rust
//! Generated by greeter-pack.
pub fn say_hello() -> String {
    "Hello, world!".to_string()
}
```

`src/farewell.rs` contains:

```rust
//! Generated by farewell-pack.
pub fn say_goodbye() -> String {
    "Goodbye, world!".to_string()
}
```

Both files landed from a single `sync run` — one pack never overwrote or
interfered with the other's output.

## 7. Check the lockfile

```bash
cat ggen.lock
```

```
# ggen.lock — generated by `ggen sync`. Do not edit.

[packs.farewell-pack]
source = "path:../farewell-pack"
content_hash = "blake3:3a5273f8d7ad156c24d3113174eb979cf485587439d34e7c9d7d035c5e071aac"

[packs.greeter-pack]
source = "path:../greeter-pack"
content_hash = "blake3:be1d7ac715f5c839483cdf4318891234164e6054e8ebad69cdfa6ca8fb1ca81a"
```

Notice `farewell-pack` is listed before `greeter-pack` — alphabetical order,
regardless of the order you declared them in `ggen.toml`. `ggen.lock` is
written sorted by pack name with one BLAKE3 content hash per pack
(`crates/ggen/src/pack.rs:313-345`), and this exact two-pack,
alphabetical-lock shape is what the project's own pairwise pack matrix test
asserts for every pack pair it drives
(`crates/ggen/tests/cross_pack_matrix.rs:222-233`).

## What you built

You built two independent packs — `greeter-pack` and `farewell-pack`, each
with its own ontology, template, and output path — declared both in one
consuming project's `[packs]` table, and ran one `ggen sync run` that
generated both outputs in a single pass, locking both packs alphabetically
in `ggen.lock`.

Now that you can compose packs, see the how-to guide for resolving output
path collisions and ordering conflicts when packs *aren't* disjoint:
[How to Resolve Pack Conflicts](../how-to/resolve-pack-conflicts.md).
