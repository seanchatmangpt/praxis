# Tutorial: Your First Pack

In this tutorial you will build a **pack** from scratch — a reusable bundle of
an ontology and templates — and consume it from a separate project. By the
end you will have run a real `ggen sync` and inspected the generated file and
lockfile it produced.

This tutorial works entirely in a scratch directory. It does not touch any
files inside the `praxis` repository itself.

## Before you start

You need the `ggen` binary built. From the repository root:

```bash
cargo build -p ggen
```

This produces `target/debug/ggen`. Every command below invokes that binary by
its full path, so you do not need to install anything.

## Step 1: Create a scratch workspace

Create a temporary directory to hold both the pack and the project that will
consume it — they live side by side because a pack is referenced by a
relative `path`.

```bash
mkdir -p /tmp/ggen-first-pack/greeting-pack/templates
mkdir -p /tmp/ggen-first-pack/hello-project/templates
```

You now have two empty directories: `greeting-pack` (the pack you're
building) and `hello-project` (the project that will use it).

## Step 2: Write the pack manifest

A pack is a directory containing exactly three things: a `pack.toml`
manifest, an `ontology.ttl`, and a `templates/` directory of `*.tmpl` files.
This is documented directly above the pack resolver:

> "A pack is a directory containing `pack.toml`, `ontology.ttl`, and a
> `templates/` directory of `*.tmpl` files."
(`crates/ggen/src/pack.rs:3-4`)

Create the manifest:

```bash
cat > /tmp/ggen-first-pack/greeting-pack/pack.toml <<'EOF'
[pack]
name = "greeting"
version = "0.1.0"
description = "Tutorial pack: generates a greeting function per Person in the graph."
EOF
```

The `[pack]` table accepts exactly three keys — `name`, `version`,
`description` — and nothing else, because the on-disk schema is declared
with `#[serde(deny_unknown_fields)]` (`crates/ggen/src/pack.rs:44-50`). If you
misspell a key or add an extra one, resolution will fail closed with an
`FM-PACK-003` error (`crates/ggen/src/pack.rs:111-120`).

## Step 3: Write the pack's ontology

The pack ships its own RDF ontology in Turtle. This is the domain the pack's
templates generate code from. Create `ontology.ttl`:

```bash
cat > /tmp/ggen-first-pack/greeting-pack/ontology.ttl <<'EOF'
@prefix dom:  <http://example.com/ontology#> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

dom:Person
    a          rdfs:Class ;
    rdfs:label "Person" .

dom:hasName
    a            rdf:Property ;
    rdfs:domain  dom:Person ;
    rdfs:range   <http://www.w3.org/2001/XMLSchema#string> .
EOF
```

This declares a `Person` class with a `hasName` property. It does not declare
any actual `Person` instances yet — those will come from the *consuming*
project's own ontology in Step 6. A pack resolves to `[FM-PACK-004]` if
`ontology.ttl` is missing (`crates/ggen/src/pack.rs:122-132`).

## Step 4: Write the pack's template

Create the `templates/` directory content — a single `one.tmpl`:

```bash
cat > /tmp/ggen-first-pack/greeting-pack/templates/one.tmpl <<'EOF'
---
to: src/greetings.rs
sparql:
  people: "SELECT ?name WHERE { ?p a <http://example.com/ontology#Person> ; <http://example.com/ontology#hasName> ?name } ORDER BY ?name"
---
//! Generated by the greeting-pack `one.tmpl` template. Do not edit.

{% for row in results %}pub fn greet_{{ row.name | snake_case }}() -> String {
    "Hello, {{ row.name }}!".to_string()
}

{% endfor %}
EOF
```

A template file is a `---`-delimited YAML frontmatter block followed by a
Tera body (`crates/ggen/src/template.rs:2-5`). The frontmatter key set is
closed the same way `pack.toml`'s is: unknown keys are a hard parse error
(`crates/ggen/src/template.rs:25-26`). Here you're using two keys:

- `to` — the output path, relative to the *consuming* project's root
  (`crates/ggen/src/template.rs:28-29`)
- `sparql` — a named SELECT query whose rows become the `results` array in
  the template body (`crates/ggen/src/template.rs:31-32`)

A pack resolves to `[FM-PACK-005]` if `templates/` contains zero `*.tmpl`
files (`crates/ggen/src/pack.rs:145-154`).

Your pack directory is now complete:

```bash
find /tmp/ggen-first-pack/greeting-pack -type f
```

```
/tmp/ggen-first-pack/greeting-pack/pack.toml
/tmp/ggen-first-pack/greeting-pack/ontology.ttl
/tmp/ggen-first-pack/greeting-pack/templates/one.tmpl
```

## Step 5: Create the consumer project's manifest

Now switch to `hello-project` — this is the project that will *consume* the
pack you just built. Write its `ggen.toml`:

```bash
cat > /tmp/ggen-first-pack/hello-project/ggen.toml <<'EOF'
[project]
name = "hello-project"

[ontology]
source = "ontology.ttl"

[packs]
greeting = { path = "../greeting-pack" }

[templates]
dir = "templates"
EOF
```

The `[packs]` table maps a pack name (`greeting`, the key you choose) to a
source reference. `{ path = "…" }` is a local pack, resolved relative to the
directory containing `ggen.toml` (`crates/ggen/src/config.rs:53-58`, and
`crates/ggen/src/pack.rs:86-88` — `resolve_path_pack` joins `config_root` with
the path). The key you write in `[packs]` — `greeting` — is authoritative;
the `name` field inside the pack's own `pack.toml` is informational only
(`crates/ggen/src/pack.rs:156-158`).

## Step 6: Give the consumer project its own ontology data

The pack defined the `Person` *class*. The consuming project supplies actual
`Person` *instances*. Create `ontology.ttl`:

```bash
cat > /tmp/ggen-first-pack/hello-project/ontology.ttl <<'EOF'
@prefix dom: <http://example.com/ontology#> .

dom:p1 a dom:Person ;
    dom:hasName "Ada" .

dom:p2 a dom:Person ;
    dom:hasName "Grace" .
EOF
```

At sync time, `ggen` loads this ontology first, then unions in every
resolved pack's ontology into the same graph
(`crates/ggen/src/sync.rs:113-134`) — so the pack's template query, which
matches on `dom:Person`/`dom:hasName`, sees the instances you just declared
here.

The project's own `templates/` directory can stay empty for this tutorial —
`ggen` only requires it to *exist* (`crates/ggen/src/sync.rs:365-384`); zero
templates in it is fine, only a *pack's* `templates/` must be non-empty.

## Step 7: Run a dry-run sync

Before writing anything, preview what sync would do. From inside
`hello-project`:

```bash
cd /tmp/ggen-first-pack/hello-project
/Users/sac/praxis/target/debug/ggen sync run --dry-run
```

Real output from this exact command:

```json
{
  "decisions": {
    "src/greetings.rs": "planned: write (dry-run)"
  },
  "graph_hash_hex": "29eb0236623293c91ee2765d8ed8a313bf837f69acff482e8b8ab06387d49744",
  "packs": {
    "greeting": "636914e7ff93add65d65b75859b47862acfef21cfe4bcb18359db07b7a2ff839"
  },
  "skipped": [],
  "written": [
    "src/greetings.rs"
  ]
}
```

`ggen sync run` maps to the five-stage pipeline — resolve, enrich, extract,
render, write (`crates/ggen/src/sync.rs:1`) — and `--dry-run` computes every
write decision without touching the filesystem or emitting a receipt
(`crates/ggen/src/sync.rs:42-43`). The `packs` map in the report is the
resolved pack's content hash (`crates/ggen/src/sync.rs:223-231`) — the same
BLAKE3 hash that will be written into the lockfile.

## Step 8: Run the real sync

Now run it for real (no `--dry-run`):

```bash
/Users/sac/praxis/target/debug/ggen sync run
```

Real output:

```json
{
  "decisions": {
    "src/greetings.rs": "written"
  },
  "graph_hash_hex": "29eb0236623293c91ee2765d8ed8a313bf837f69acff482e8b8ab06387d49744",
  "packs": {
    "greeting": "636914e7ff93add65d65b75859b47862acfef21cfe4bcb18359db07b7a2ff839"
  },
  "skipped": [],
  "written": [
    "src/greetings.rs"
  ]
}
```

## Step 9: Inspect the pack's output landing in your project

The pack's template rendered `src/greetings.rs` inside `hello-project` — not
inside the pack. Look at it:

```bash
cat src/greetings.rs
```

Real output:

```rust
//! Generated by the greeting-pack `one.tmpl` template. Do not edit.

pub fn greet_ada() -> String {
    "Hello, Ada!".to_string()
}

pub fn greet_grace() -> String {
    "Hello, Grace!".to_string()
}

```

Both `greet_ada` and `greet_grace` came from the two `Person` instances you
wrote into `hello-project/ontology.ttl` in Step 6 — the pack's SPARQL query
and Tera loop did the rest.

## Step 10: Inspect the generated lockfile

Sync also wrote a `ggen.lock` at the project root. This is the "Write" side
of pack resolution: on every non-dry-run sync, `ggen` chains the resolved
pack's content hash into the lockfile
(`crates/ggen/src/sync.rs:235-239`, `crates/ggen/src/pack.rs:313-345`).

```bash
cat ggen.lock
```

Real output:

```
# ggen.lock — generated by `ggen sync`. Do not edit.

[packs.greeting]
source = "path:../greeting-pack"
content_hash = "blake3:636914e7ff93add65d65b75859b47862acfef21cfe4bcb18359db07b7a2ff839"
```

The `source` string records exactly how the pack was referenced —
`path:../greeting-pack`, built by `source_string` from your `[packs]` entry
(`crates/ggen/src/pack.rs:239-244`). The `content_hash` is a deterministic
BLAKE3 over the pack's `ontology.ttl` and every template file, computed as
sorted `(relative_path, bytes)` pairs (`crates/ggen/src/pack.rs:169-172`,
`:177-202`). On every future sync, `ggen` checks this hash against the pack
currently on disk and fails closed — `[FM-PACK-008]` — if the pack changed
without an intentional re-lock (`crates/ggen/src/pack.rs:268-311`).

## What you built

You built a minimal, complete pack — a `pack.toml` manifest, an
`ontology.ttl` domain, and one Tera template — and consumed it from a
separate project via `{ path = "…" }` in `[packs]`. You ran both a dry-run
and a real `ggen sync`, watched the pack's template render a file into the
*consumer's* project tree using data from the *consumer's* own ontology, and
read the real `ggen.lock` entry that pins the pack's content hash.
