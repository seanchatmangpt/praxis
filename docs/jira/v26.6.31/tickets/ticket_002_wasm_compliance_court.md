# Ticket: Build WASM-Based Compliance Court for Receipt Verification

## Title
Build WASM-Based Compliance Court for Receipt Verification (PROJ-102)

## Description
To establish a Zero-Trust verification model for system events and build logs, we will construct a WebAssembly (WASM)-based compliance court (`wasm-court`). This court runs inside the `cargo-cicd` pipeline as an isolated boundary, protecting the execution environment from untrusted runners or dynamic script tampering.

The `wasm-court` module must read the output diagnostic logs/receipts generated by the system (including the OCEL 2.0 logs produced by the impossibility sensors) and verify their cryptographic signatures and schema integrity against canonical definitions. Specifically, the court checks the signatures against the `receipt.schema.json` schema and uses `v1.json` for validation rules.

Key responsibilities:
1. Read the input `CommandReceipt` or `PiReceipt` structures.
2. Verify ed25519 signatures using public keys defined in the SPKI configuration.
3. Validate schema integrity using `receipt.schema.json`.
4. Enforce the three type-drift mitigations defined in `v1.json`:
   - **Run ID Naming**: Enforce strict naming conventions for execution run identifiers to prevent run-spoofing.
   - **Timing Asymmetry Mapping**: Analyze and validate telemetry timestamps to detect and reject anomalous timing drift or retrofitted logs.
   - **Bare 64-character BLAKE3 Hash Extraction**: Extract and verify the exact 64-character BLAKE3 hash of source artifacts to ensure strict code lineage.
5. Return a non-zero exit code if any verification check fails.

## Acceptance Criteria
- **WASM Compilation**: The verification court must compile to the `wasm32-unknown-unknown` target.
- **Headless Execution**: The WASM binary must be runnable via a headless WASM runtime such as `wasmtime` or `wasmer`.
- **Cryptographic Signature Verification**: The court must successfully verify ed25519 signatures contained inside the `CommandReceipt` JSON data structures. Invalid signatures must trigger a failure.
- **Type-Drift Compliance**: The code must strictly implement and enforce the three type-drift mitigations parsed from `v1.json`:
  - Run ID naming pattern validation.
  - Timestamp asymmetry checks (comparing FFI execution time against system time within strict thresholds).
  - BLAKE3 hash integrity confirmation (must be a valid, 64-character hex string corresponding to the verified payload).
- **Zero-Trust Failsafe**: Any validation failure (schema mismatch, invalid signature, or mitigation violation) must result in a non-zero exit status, failing the host CI/CD process.

## Dependencies
- `ticket_001_impossibility_sensors` (PROJ-101)

## Verification Mechanism
Verify the WASM compliance court through the following objective tests:
1. Compile the court package to WebAssembly:
   ```bash
   cargo build --package wasm-court --target wasm32-unknown-unknown --release
   ```
2. Run the integration test suite validating signature and schema conformance:
   ```bash
   cargo test --test wasm_court_conformance
   ```
3. The test suite in `tests/wasm_court_conformance.rs` must:
   - Execute the compiled `wasm-court` module against valid receipts and assert a successful validation (exit code 0).
   - Inject a tampered or invalid signature into a test receipt, execute the court, and assert that the validator fails with a non-zero exit code.
   - Inject a payload violating the BLAKE3 hash length or the timing asymmetry window and assert that validation fails.
