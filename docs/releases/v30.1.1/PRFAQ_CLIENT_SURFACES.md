## Praxis Adds Working Web and Mobile Control Surfaces for Blue River Dam

Pasadena, CA — Praxis today announced the first working client surfaces for Blue
River Dam, the deterministic control system for AI-generated technical work.

The release pulls forward existing working Next.js, Expo, and Nuxt code into the
Praxis ecosystem as official control and publication surfaces. Next.js and Expo are
active first. Nuxt is included as the third shell surface where existing working
code is available and reconciled into the release inventory.

Praxis is no longer only a command-line verification factory. Praxis now has
visible control rooms.

- Next.js becomes the enterprise web control room.
- Expo becomes the mobile operator console.
- Nuxt becomes the experimental browser shell and world-manufacturing interface.

The core system remains deterministic. GraphLaw owns law-state. PDDL owns planning.
POWL owns workflow. bcinr owns hot-path transition control. ggen owns artifact
manufacturing. Lean, Lake, tests, and validators own verification. Receipts own
evidence.

The clients do not create standing. They show standing. They command lawful
actions. They inspect receipts. They display flow. They publish reports.

## The Customer Problem

Enterprises adopting AI agents do not only need better generation. They need
control. AI systems now generate code, reports, tests, plans, policies, issues,
proofs, documentation, compliance drafts, and deployment artifacts faster than
teams can accept them. The result is uncontrolled flow: work piles up, artifacts
lose provenance, teams cannot see what has standing, review queues grow,
verification becomes manual, compliance evidence is reconstructed after the fact.

Praxis solves this by making generated work enter a deterministic standing factory.
But a factory also needs control surfaces. That is what this release adds.

## The Product

### Next.js Control Room

The Fortune 5 web control room, for enterprise operators, engineering leaders,
release managers, compliance reviewers, and buyers. It shows: current WIP, arrival
rate, time to standing, standing distribution, blocked artifacts, verifier
bottlenecks, receipt status, planner state, workflow state, Divan control benchmark
reports, release readiness, arXiv readiness, Fortune 5 pilot readiness.

It answers the enterprise question: what generated work has standing right now?

### Expo Mobile Console

The mobile operator console, for fast review, field inspection, approval/refusal
workflows, receipt lookup, and operational alerts. It shows: artifact standing,
receipt details, blocked states, legal next actions, workflow alerts, planner
updates, verification results, release-gate status.

The mobile console does not turn the phone into authority. It turns the phone into
a portable window into authority. Authority remains in Praxis standing.

### Nuxt Browser Shell

The browser shell and experimental world-manufacturing interface: richer
interactive demos, post-cyberpunk product presentation, browser-native control
surfaces, world-style visualization of GraphLaw, workflows, receipts, and generated
artifacts. Where Next.js is the enterprise control room, Nuxt is the experimental
civic interface. Where Expo is mobile command, Nuxt is immersive inspection.

## The Important Boundary

The clients are not the dam. They are windows into the dam. The dam is GraphLaw,
PDDL, POWL, bcinr, ggen, verifiers, receipts, reports.

The clients may display state, call commands, trigger lawful workflows, request
reports, inspect receipts, show benchmarks, visualize queues. But they do not
create truth. They do not invent status. They do not locally decide standing.

Every badge, chart, queue, button, and report must map to one of: GraphLaw fact,
planner state, POWL workflow state, bcinr transition result, ggen artifact,
verifier output, receipt, generated report. If the UI cannot point to one of those,
the UI is not allowed to present the value as standing.

## Little's Law as the Dashboard Standard

The control room must answer Little's Law questions: how much work is in the
system, how fast is work arriving, how long to standing, where is work waiting,
which gate is the bottleneck, what happens when generation doubles, which queue is
growing, which artifacts are blocked/verified/receipt-missing/ready to publish.

Ordinary AI dashboards show activity. Praxis shows flow control. The Next.js
dashboard makes this visible; the Expo console makes it portable; the Nuxt shell
makes it explorable.

## The Demo

The demo begins in the Next.js control room. The operator sees generated work
entering the system. One target artifact is blocked; the dashboard shows why. The
operator opens the planner state. PDDL identifies the next lawful action. POWL
compiles the workflow. bcinr executes the transition path. ggen manufactures the
artifact. The verifier runs. A receipt is written. GraphLaw updates. The dashboard
changes. The Expo app receives the updated standing. The report is published.

The system did not merely run an agent. It moved work through lawful standing.

## Customer Promise

Every AI-generated technical artifact shown in the control room has standing,
refusal, blocker, receipt, or declared unknown state. No dashboard fiction. No
ungrounded green checkmarks. No agent self-report as authority. No local UI status
pretending to be truth. No compliance claim without evidence. No generated work

## What This Is Not

This is not a UI rewrite, a new frontend project, a dashboard pasted onto an
unproven backend, a simulation of trust, or a local state machine pretending to be
authority. This release pulls forward working code and assigns it proper standing:
existing Next.js, Expo, and Nuxt surfaces are inspected, classified, wired, or
typed (ALIVE / PARTIAL / BLOCKED / STALE / DUPLICATE / OUT_OF_SCOPE / UNKNOWN). No
vague frontend inventory. No hand-fitted demo.

## Product Architecture

Praxis core manufactures standing. Client surfaces inspect standing. Next.js is
the enterprise control room; Expo is the mobile operator console; Nuxt is the
browser shell. The clients talk to Praxis through declared surfaces: they read
reports, receipts, and GraphLaw-derived state; they invoke planner/workflow
commands only through lawful adapters; they render benchmark evidence; they publish
release state. They never become the source of truth.

## Release Acceptance
