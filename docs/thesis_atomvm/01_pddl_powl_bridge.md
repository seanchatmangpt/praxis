# Chapter 1. From Possibility to Execution: The PDDL-POWL Semantic Bridge

## 1.1 Introduction
In the relentless pursuit of truly autonomous computing systems, the chasm between formal action planning and concrete, systemic execution has historically been bridged by brittle, handcrafted procedural code—a layer broadly and colloquially termed "business logic." This chapter establishes the foundational theoretical architecture of the AtomVM by formalizing a direct, provable semantic bridge between the Planning Domain Definition Language (PDDL) and the Process Ontology for Web Languages (POWL) version 2. By treating PDDL as the definitive boundary of possibility and POWL as the rigorous, executable substrate for state transition, we define a computational stack where human-authored business logic is entirely bypassed in favor of mathematically verifiable graph transformations. This represents a paradigm shift from ad-hoc procedural approximation to formal systemic execution.

## 1.2 The Epistemology of Action in PDDL
Classical automated planning, anchored by PDDL since its inception, relies on a strict separation of domain physics and problem instantiations. The domain definition, formally denoted as $\mathcal{D} = \langle \mathcal{P}, \mathcal{A} \rangle$, encapsulates the finite set of predicates $\mathcal{P}$ and the set of parameterized actions $\mathcal{A}$. An action $a \in \mathcal{A}$ is formally defined by its preconditions $Pre(a)$ and its effects $Eff(a)$, which are often subdivided into positive assertions $Eff^+(a)$ and negative retractions $Eff^-(a)$. 

In this ontological paradigm, PDDL does not merely describe what *might* happen within a system; rather, it formally delineates the absolute boundaries of possibility within a given universe of discourse. Under the closed-world assumption typical of classical STRIPS and ADL variants, any state transition not explicitly derivable from the iterative application of instantiated actions in $\mathcal{A}$ is categorically impossible. PDDL effectively bounds the operational physics of the domain. 

However, PDDL is inherently declarative and fundamentally decoupled from the actual mechanics of execution. It constructs a theoretical state-space graph where nodes are sets of grounded predicates and edges represent valid action transitions. Yet, when a heuristic search or SAT-based planner synthesizes a valid plan $\pi = \langle a_1, a_2, \ldots, a_n \rangle$, the execution of $\pi$ within a real-world software environment traditionally demands a translation layer. Historically, this layer has been inhabited by human software engineers who interpret the declarative plan and encode it into imperative or object-oriented business logic. This manual translation is the primary locus of semantic degradation, introducing implicit assumptions, race conditions, and unmodeled state inconsistencies that routinely violate the formal guarantees provided by the planner.

## 1.3 The Semantic Grounding Problem and the Fallacy of Business Logic
The term "business logic" is a colloquialism for the ad-hoc procedural rules that govern state mutations in traditional software architectures (e.g., MVC or microservice patterns). From a rigorous formal perspective, human-written business logic acts as an uncontrolled source of entropy. It attempts to heuristically approximate the strict precondition-effect contracts of planning actions through deeply nested conditional statements, isolated database transactions, and brittle error-handling routines. 

The core issue is the semantic grounding problem: the abstract predicates of a PDDL domain must be bound to the concrete state of an executing system. If the system's state is represented across relational database tables or scattered within an in-memory object graph, the mapping from PDDL predicates to these heterogeneous data structures is almost always non-isomorphic and heavily lossy. The imperative execution layer lacks the structural homomorphism required to maintain the invariants of the planning layer. To achieve true machine autonomy, the state representation must be natively propositional, and the execution of an action must manifest as an atomic, mathematically defined state mutation. Human-written business logic, with its infinite Turing-complete permutations and lack of formal verification, cannot satisfy these rigorous constraints.

## 1.4 POWL v2 as the Substrate for Executable Semantics
To decisively resolve the semantic grounding problem, the AtomVM architecture discards imperative business logic entirely, adopting the Process Ontology for Web Languages (POWL) version 2 as its primary execution substrate. POWL v2 is expressed natively in the Terse RDF Triple Language (Turtle or TTL) syntax, providing a highly rigorous Resource Description Framework (RDF) graph representation of both systemic state and active process.

In the POWL v2 paradigm, the state of the universe is not a disjointed collection of tables or volatile objects, but a unified, directed labeled graph $G = \langle V, E \rangle$, where $V$ represents a set of Uniform Resource Identifiers (URIs) and literal values, and $E$ represents semantic relationships (predicates). A TTL graph provides a meticulously bounded snapshot of reality at any discrete time $t$. Processes in POWL are defined as parameterized graph transformations, conceptually aligned with the Semantic Web Rule Language (SWRL) but vastly extended with temporal, transactional, and execution semantics.

Crucially, POWL v2 is not merely a descriptive ontology; it is a fully *executable* environment. The AtomVM engine is designed to interpret POWL graphs directly. A POWL process defines exactly how a target subgraph must be mutated—explicitly defining which triples are to be retracted and which are to be asserted—upon execution. This provides the mathematically ideal target for a formal mapping from PDDL.

## 1.5 The Semantic Bridge: Homomorphic Mapping from PDDL to POWL
The PDDL-POWL bridge forms the first and most critical layer of the AtomVM stack. It operates via a direct, homomorphic compiler that seamlessly translates PDDL domain definitions into executable POWL v2 process graphs, ensuring zero loss of formal semantics.

First, consider the ontological mapping: every PDDL predicate $P(x_1, \ldots, x_k)$ is mapped directly to an RDF triple pattern or a localized subgraph schema in TTL. The object hierarchies and typing systems defined in the PDDL domain translate cleanly into an RDF Schema (RDFS) or Web Ontology Language (OWL) class hierarchy. Consequently, the state of the world in PDDL becomes perfectly isomorphic to the asserted triples within the POWL graph environment. A grounded predicate is mathematically equivalent to the existence of a specific directed edge in the TTL graph.

Second, the operational mapping: a parameterized PDDL action $a$ is translated into a POWL v2 `powl:Transition`. The preconditions $Pre(a)$ are compiled into a strict subgraph matching query. This is conceptually identical to a highly optimized SPARQL `ASK` or `SELECT` query. The execution environment evaluates this query against the current TTL state graph. If the graph matches, yielding a valid variable binding $\theta$, the precondition is provably satisfied. 

The effects $Eff(a)$ are simultaneously compiled into a SPARQL `UPDATE` equivalent. This dictates the precise retraction of triples (mapping to negative effects, $Eff^-(a)$) and the assertion of new triples (mapping to positive effects, $Eff^+(a)$). Let us formalize this operational sequence. For an action $a$ executing under a valid binding $\theta$:
1. $Pre(a)\theta \implies \text{MatchGraph}(G, Q_{Pre(a)\theta})$
2. $Eff^-(a)\theta \implies G' = G \setminus \Delta^-$
3. $Eff^+(a)\theta \implies G'' = G' \cup \Delta^+$

Because both PDDL and POWL v2 operate fundamentally on symbolic, relational state models, this mapping requires absolutely zero semantic interpretation by human software engineers. The translation is mechanical, logically provable, and immediate. Existential and universal quantifications in PDDL preconditions map directly to graph traversal patterns and negation-as-failure (or scoped closed-world evaluations) within the POWL semantic constraints.

## 1.6 Zero-Code Execution and the Foundational Architecture of AtomVM
By bridging PDDL and POWL v2, AtomVM achieves what we formally term "zero-code execution." The domain expert, or increasingly, an upstream automated knowledge-acquisition system, defines the bounds of possibility entirely in PDDL. The AtomVM compiler translates this possibility space directly into executable TTL graphs. When a planner generates a sequence of actions, the AtomVM execution engine simply processes the corresponding sequence of POWL transitions against the unified state graph.

Within this stack, there is no intermediate procedural language. There are no REST controllers, no brittle service layers, and absolutely no Object-Relational Mappers (ORMs). The entire middle tier of traditional software architecture—the historical locus of human business logic—is surgically excised. 

The resulting system is inherently safe and formally verified by construction. It is mathematically impossible for the execution engine to mutate the state in a way that violates the physics defined by the PDDL domain. If an action's translated POWL precondition graph does not perfectly match the current state graph at execution time, the transition simply cannot fire. The execution environment is strongly coupled to the planner's formal guarantees.

## 1.7 Conclusion
The PDDL-POWL Semantic Bridge constitutes the absolute bedrock of the AtomVM architecture. By strictly constraining the definition of systemic possibility to the rigorously formal PDDL syntax, and subsequently mapping it homomorphically into the graph-theoretic, executable space of POWL v2, we have definitively eliminated the need for fragile human translation. This architecture ensures that what is planned is precisely what is executed, down to the fundamental atomic level of graph state mutation. In bypassing human business logic entirely, AtomVM establishes a pristine foundation for autonomous computation. In the subsequent chapters, we will explore how this robust foundational layer supports hierarchical task networks, temporal planning constraints, and real-time ontological reflection within the broader AtomVM ecosystem.
