# praxis v2030.1.1 — PRD / ARD

**Depends on:** `ggen`

**Standing conferred:** `UNKNOWN`.

## Product requirement

`praxis` SHALL be the fleet-scale conformance system that determines whether repositories, generated surfaces, capabilities, interfaces, deployments, evidence, and release subjects satisfy the Chatman Ecosystem's operational laws. By v2030.1.1 it must make conformance across hundreds of repositories queryable and executable instead of relying on manual audits.

## Required capabilities

1. Discover exact repository/ref/tree subjects and preserve source identity.
2. Evaluate ecosystem invariants including `A = μ(O*)`, zero unreceipted actuation, SELECT/CONSTRUCT/DO separation, generated-source ownership, typed refusals, deterministic receipt/replay, and evidence-bounded standing.
3. Detect missing public/custom ontology, missing generation correspondence, CLI/API/MCP/A2A divergence, unreceipted actuation, stale docs, stale dependencies, unreconstructable repositories, and unfinished governed WIP.
4. Represent conformance as typed findings with exact subject/path/rule/evidence rather than aggregate scores alone.
5. Support DfCM fleet repair: preserve all independent repair edges and choose minimal dependency-closed repair sets.
6. Manufacture repair candidates through ggen/pack knowledge where lawful, but keep repair CONSTRUCT separate from DO.
7. Re-run the narrowest owning verifier after repair and propagate evidence into fleet standing only when the exact subject executed.
8. Produce machine-readable fleet reports suitable for `chatman-ecosystem` release composition.

## Architecture requirements

```text
fleet subjects + doctrine + canonical rules
      -> observation graph
      -> conformance admission
      -> rule/closure evaluation
      -> typed findings
      -> repair candidates
      -> owning repo verifier
      -> receipt
      -> fleet standing projection
```

A repository is not ALIVE because Praxis can inspect it. Conformance inspection, generated repair, execution, and independent verification SHALL remain separate evidence classes.

## Acceptance for v2030.1.1

- a fleet scan can bind exact SHAs and enumerate required repo capabilities;
- rules identify missing/broken semantic edges with stable typed outcomes;
- generated/manual authority boundaries are respected during repair planning;
- representative repo families can be reconstituted and checked for CLI/API/MCP/A2A/ontology/receipt closure;
- repair proposals preserve unrelated work and do not weaken negative fixtures;
- fleet reports distinguish UNKNOWN, PARTIAL_ALIVE, ALIVE, BLOCKED, BUILD_BROKEN, UNSUPPORTED, and typed REFUSED outcomes;
- release aggregation never upgrades component standing beyond owning verifier evidence.

## Falsifiers

The architecture is falsified if fleet conformance is inferred from repository metadata without examining exact subjects; if one failed transport or repo edge marks the entire fleet failed; if a generated repair bypasses the owning source authority; or if a central score hides missing execution evidence.

## Ecosystem contract

Praxis evaluates and coordinates fleet conformance. Owning repositories retain semantic, implementation, formal, runtime, and verification authority. `chatman-ecosystem` consumes Praxis evidence for composition; Praxis does not mint crown standing on behalf of component verifiers.
